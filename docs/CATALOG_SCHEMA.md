# Catalog schema (interface v0)

This is the field-by-field contract for the two catalog documents. What `v0`
promises as an interface — the asset naming convention and the HBIOS host
extension ABI — is in [INTERFACE_V0.md](INTERFACE_V0.md); this file covers only
the JSON.

Both documents are generated by `tools/gen_catalog.py` from the built
artifacts. Every `size` and every `sha256` in them is computed from the file
that will actually be uploaded (`tools/gen_catalog.py:141-142`, `:171-172`);
nothing is transcribed by hand. `tools/verify_catalog.py` re-derives the same
claims independently and can be run against a directory of downloaded assets.

The committed copies under `catalog/v0/` are byte-identical to the published
assets, so they can be read and diffed without fetching anything. The legacy
XML is written only to `build/`, not committed.

## 1. The two documents and how a client walks them

There are two levels: an index that lists RomWBW versions, and one catalog per
RomWBW version that lists that version's ROMs and disks.

**Step 1 — fetch the index.** One stable URL, compiled into the client:

    https://github.com/avwohl/romwbw_disks/releases/download/catalog-v0/index-v0.json

The `catalog-v0` tag carries this one small file and nothing else. Big
artifacts never live on it, so re-cutting it costs one upload of a few
kilobytes. That is what makes a floating entry point safe: the thing that moves
is tiny, and the things clients cache never move.

**Step 2 — pick a RomWBW version.** Walk `romwbw_versions[]` and keep the
entries this build can actually run. Every released client today keeps the one
entry whose `hbios.ver_byte` / `hbios.upd_byte` match the single release its
bundled emulator core was built for. A client rebuilt on `romwbw_emu` v1.39 or
later keeps every entry its core says it can run, and offers the list — see
§2.3.

**Step 3 — fetch that entry's `catalog_url`.** It is an absolute URL already;
do not build it. For 3.5.1:

    https://github.com/avwohl/romwbw_disks/releases/download/v0-romwbw-3.5.1/catalog-v0-3.5.1.json

The index carries that catalog's `catalog_sha256` and `catalog_size`, so the
download can be verified before it is parsed.

**Step 4 — fetch assets as `base_url` + `filename`.** `base_url` in the catalog
ends with `/` (`tools/gen_catalog.py:125`). Concatenate directly; do not insert
another separator.

    https://github.com/avwohl/romwbw_disks/releases/download/v0-romwbw-3.5.1/  +  hd1k_combo-v0-3.5.1.img

Every entry carries its own `sha256` and `size` for verification after the
download.

A client that has not yet learned the JSON can instead fetch the entry's
`disks_xml_url`, which is the same disk list in the shape it already parses.
See §5.

## 2. index-v0.json

### 2.1 Top level

| Field | Type | Meaning |
|---|---|---|
| `schema` | string | Always `"romwbw-disks-index"`. Distinguishes this document from a per-version catalog. |
| `schema_version` | integer | Currently `1`. Bumped only if the *shape* of this document changes incompatibly. Independent of `interface`. |
| `interface` | string | The interface version this index describes. Currently `"v0"`. |
| `repo` | string | `"https://github.com/avwohl/romwbw_disks"`. Where the sources and this document come from. |
| `index_url` | string | The canonical URL of this document, self-referentially. A client that has a copy from somewhere else can tell where the live one lives. |
| `romwbw_versions` | array of object | One entry per published RomWBW version, in the order `tools/gen_catalog.py` walked `versions/` (sorted by directory name). |

### 2.2 A `romwbw_versions[]` entry

| Field | Type | Meaning |
|---|---|---|
| `romwbw_version` | string | The upstream RomWBW release, e.g. `"3.5.1"`. This is the second axis of the two-level catalog and the `<ver>` in every asset name. |
| `label` | string | Display string, `"RomWBW " + romwbw_version` (`tools/gen_catalog.py:273`). For a menu. Do not parse it. |
| `status` | string | `"stable"` or `"preview"` today. Copied from `versions/<ver>/version.json`. Not a closed set — see §6. |
| `default` | boolean | The version to select when the user has no preference. The index promises exactly one entry with `true`; `tools/verify_catalog.py:165-167` fails the release otherwise. |
| `released` | string or null | Upstream release date, `YYYY-MM-DD`. `"2025-05-21"` for 3.5.1, `"2026-03-28"` for 3.6.0. Read with `.get()` (`tools/gen_catalog.py:276`), so null if a version file omits it. |
| `hbios` | object | The version bytes for this release. See §2.3. |
| `release_tag` | string | The immutable GitHub tag holding this version's assets, `v0-romwbw-<ver>`. |
| `catalog_url` | string | Absolute URL of `catalog-v0-<ver>.json`. |
| `catalog_sha256` | string | 64 lowercase hex characters. The hash of the document at `catalog_url`. |
| `catalog_size` | integer | Bytes of that document. `11826` for 3.5.1, `14694` for 3.6.0. |
| `generation` | integer | Copy of the catalog's `generation`. See §4. Present here so a client can decide whether to re-fetch a catalog it already has. `tools/verify_catalog.py:181-183` fails the release if the two disagree. |
| `disks_xml_url` | string | Absolute URL of `disks-v0-<ver>.xml`, the legacy shape. See §5. |
| `rom_count` | integer | `len(roms)` in that catalog. `2` for both published versions. |
| `disk_count` | integer | `len(disks)` in that catalog. `20` for 3.5.1, `24` for 3.6.0. |
| `notes` | array of string | Free text about this version, copied from `versions/<ver>/version.json`. May be empty. Display it; never branch on it. |

`rom_count` and `disk_count` are for showing "24 disks" next to a version in a
picker without downloading the catalog. They are not a promise about what the
catalog contains beyond its length.

### 2.3 The `hbios` object, and why it is in the index

Same shape in the index entry and in the catalog — both are copied verbatim from
`versions/<ver>/version.json` (`tools/gen_catalog.py:201`, `:277`).

| Field | Type | Meaning |
|---|---|---|
| `major` | integer | RomWBW `RMJ`. `3`. |
| `minor` | integer | RomWBW `RMN`. `5` for 3.5.1, `6` for 3.6.0. |
| `update` | integer | RomWBW `RUP`. `1` for 3.5.1, `0` for 3.6.0. |
| `patch` | integer | RomWBW `RTP`. `0` for both. |
| `ver_byte` | string | `"0x35"` / `"0x36"`. `(major << 4) | minor`, as a hex **string**, not an integer. |
| `upd_byte` | string | `"0x10"` / `"0x00"`. `(update << 4) | patch`, likewise a string. |
| `sysver_de` | string | `"0x3510"` / `"0x3600"`. The `DE` register pair `HBF_SYSVER` returns: `D` = `ver_byte`, `E` = `upd_byte`. |

`tools/verify_catalog.py:130-131` recomputes the packed version bytes from
`major`/`minor`/`update`/`patch`, and `:146-150` compares them against the four
HCB bytes it reads at `0x103` out of the built ROM. The two hex strings reach
that ROM by the other path: `tools/build_rom.sh:32` reads `ver_byte`/`upd_byte`
out of `version.json` and `:53-54` emit them as `RMV_VER`/`RMV_UPD` for the
assembler, while `:36` recomputes the expected HCB from the four integers and
`:94-97` reads the built ROM back at `0x103` and deletes it on a mismatch. So
the four integers and the two strings cannot drift apart.

**Why these are in the index and not only in the catalog.** Whether a client
can load a ROM is decided by those two bytes. `emu_validate_rom_hcb`
(`romwbw_emu/src/emu_init.cc`) reads them out of the image at file offsets
`0x105`/`0x106` — via `emu_romwbw_release_of_image` — and returns a refusal
that `emu_load_rom` turns into a failed load.

What it refuses changed with `romwbw_emu` v1.39, and the field did not. Before
it, the bytes were compared against a compile-time `ROMWBW_PIN_VER_BYTE` /
`ROMWBW_PIN_UPD_BYTE`, so a binary built for 3.5.1 physically could not load a
3.6.0 ROM. Since it, the version is read out of the ROM at run time and one
binary boots any release in `ROMWBW_SUPPORTED_RELEASES`
(`romwbw_emu/src/romwbw_pin.h`, today 3.5.1 and 3.6.0); the refusal is reserved
for a release that core has never been run against, and names both what it
found and what it accepts. `--allow-untested-romwbw` downgrades it to a warning.

Putting the version bytes in the index means a client answers that question
from a document it has already fetched, *before* it downloads anything. Without
them it would have to fetch a catalog to find out, or worse, download a 512KB
ROM only to have its own validator refuse it. Filtering in the index costs one
already-fetched document.

A client built before v1.39 compares the two strings against its own
compile-time constants and keeps the single entry that matches. A client built
on v1.39 or later should ask its core rather than assume, since a client can be
newer or older than the core it links: keep an entry when
`emu_romwbw_release_supported({ver_byte, upd_byte})` says yes, and offer what
survives. Same field, same job; only the number of survivors differs. No
released client carries a v1.39 core yet, so in every shipped app "pick a
RomWBW version" still means "filter to the one release this binary was built
for" — and why a client must filter rather than trust `status`: 3.6.0 is
published `"status": "stable"` yet no shipped client can boot it. See
[CLIENT_MIGRATION.md](CLIENT_MIGRATION.md).

## 3. catalog-v0-&lt;ver&gt;.json

One per RomWBW version, on that version's immutable release tag.

### 3.1 Top level

| Field | Type | Meaning |
|---|---|---|
| `schema` | string | Always `"romwbw-disks-catalog"`. |
| `schema_version` | integer | Currently `1`. |
| `interface` | string | `"v0"`. |
| `romwbw_version` | string | The RomWBW release these assets are built for. `tools/verify_catalog.py:185-187` fails the release if this disagrees with where the index filed it. |
| `generation` | integer | The catalog generation for this RomWBW version. See §4. |
| `status` | string | Same value as the index entry's `status`. |
| `release_tag` | string | `v0-romwbw-<ver>`. |
| `base_url` | string | Download prefix, **ending in `/`**. Asset URL is `base_url + filename`. |
| `hbios` | object | Same shape and values as the index entry's `hbios`. See §2.3. |
| `upstream` | object | Where the stock material came from. See below. Note this is an *object*; a disk entry's `upstream` is a *string*. |
| `notes` | array of string | Same array as the index entry's `notes`. May be empty. |
| `roms` | array of object | See §3.2. |
| `disks` | array of object | See §3.3. |

The top-level `upstream` object identifies the RomWBW release package this
version was built from:

| Field | Type | Meaning |
|---|---|---|
| `tag` | string | Upstream tag, e.g. `"v3.5.1"`. |
| `package_url` | string | The `RomWBW-v<ver>-Package.zip` this build fetched. |
| `package_sha256` | string or null | Hash of that zip. `e696ff2f…` for 3.5.1, `bdf847d5…` for 3.6.0. Read with `.get()` (`tools/gen_catalog.py:205`), so a version file that omits it yields null. |

Pinning the package by hash is what keeps a dev snapshot out of a release. The
`SBC_simh_std_v360.rom` in `romwbw_emu/archive/romwbw-v3.6.0/` is a
`v3.6.0-dev.46` build from 2025-12-12 whose HCB reads `36 00` — identical to
the real release, so a version-byte check blesses it. Only the CBIOS banner
tells them apart. `tools/fetch_romwbw.sh` pulls the real package and checks
this hash.

### 3.2 A `roms[]` entry

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Stable identifier, e.g. `"emu_avw"`. Use this as the key, not the filename. |
| `filename` | string | `<id>-v0-<ver>.rom`, e.g. `"emu_avw-v0-3.5.1.rom"`. Append to `base_url`. |
| `name` | string | Display name, e.g. `"EMU AVW"`. |
| `description` | string | One or two sentences for a UI. |
| `size` | integer | Bytes. `524288` for both published ROMs. Nothing promises 512KB in general: upstream v3.6.0 ships some 256KB and 384KB ROM images, though `SBC_simh_std.rom` and `RCZ80_std.rom` are still 512KB. |
| `sha256` | string | 64 lowercase hex characters, computed from the built file. |
| `default` | boolean | Whether this is the ROM to offer first. |
| `hcb` | object | The HBIOS Configuration Block bytes, read back out of the built ROM. See below. |
| `built_from` | object | Provenance. See below. |

**`hcb`** is read from the built file at offset `0x100`
(`tools/gen_catalog.py:133-135`) and reported per byte
(`tools/gen_catalog.py:146-151`):

| Field | Type | Source | Meaning |
|---|---|---|---|
| `marker` | string | file offsets `0x103`, `0x104` | `"57 A8"` — two uppercase hex bytes separated by a space. `'W'` `0xA8`, the marker that says an HCB follows. |
| `version` | string | `0x105` | `"0x35"` / `"0x36"`. `(major << 4) | minor`. The `ver` half of the release, read back by `emu_romwbw_release_of_image` (`romwbw_emu/src/emu_init.cc`). |
| `update` | string | `0x106` | `"0x10"` / `"0x00"`. `(update << 4) | patch`. The `upd` half. `emu_validate_rom_hcb` refuses the load unless the `{ver, upd}` pair appears in `ROMWBW_SUPPORTED_RELEASES` (`romwbw_emu/src/romwbw_pin.h`). |
| `platform` | integer | `0x107` | `0`. A decimal integer, unlike `version` and `update`, which are hex strings. The asymmetry is real; do not assume a uniform encoding. |

These are the exact bytes a client's own validator will read after the download.
A client that checks them *before* fetching rejects a ROM it could not run
without spending 512KB. That is the same reason `ver_byte` and
`upd_byte` are in the index (§2.3), one level finer.

**`built_from`** says what went into the image:

| Field | Type | Meaning |
|---|---|---|
| `bank0` | string | Always `"src/emu_hbios.asm"` — our HBIOS proxy, assembled in this repo with the version bytes generated from `versions/<ver>/version.json`. |
| `banks_1_15` | string | Path inside the upstream package the remaining banks were lifted verbatim from, e.g. `"Binary/SBC_simh_std.rom"`. |

### 3.3 A `disks[]` entry

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Stable identifier, e.g. `"hd1k_combo"`. The same `id` may exist under one RomWBW version and not another — `hd1k_ws4` is in 3.5.1 and not in 3.6.0. |
| `filename` | string | `<id>-v0-<ver>.img`, e.g. `"hd1k_combo-v0-3.5.1.img"`. Append to `base_url`. |
| `name` | string | Display name, e.g. `"Combo (Recommended)"`. |
| `description` | string | One or two sentences for a UI. |
| `size` | integer | Bytes. `8388608` for a single hd1k slice, `51380224` for a combo. |
| `sha256` | string | 64 lowercase hex characters, computed from the built file. |
| `license` | string | Free text: `"Mixed"`, `"Abandonware"`, `"Freeware"`, `"Open Source"` are the values in use. Display it; do not switch on it. |
| `format` | string | `"hd1k"` or `"hd1k_combo"`. See below. |
| `bootable` | boolean | Whether the probed slice's boot track holds a system image. See below. |
| `cbios` | string or null | The CBIOS banner found in the probed slice, or null. See below. |
| `host_transfer` | boolean | Whether the probed slice carries `W8.COM` and `R8.COM`. See below. |
| `upstream` | string | Path inside `RomWBW-v<ver>-Package.zip` this image started as, e.g. `"Binary/hd1k_combo.img"`. A **string** here; the top-level `upstream` is an object. |
| `slices` | integer, optional | Present only on multi-slice images. `6` on `hd1k_combo`. Absent everywhere else. |
| `defaultSlot` | integer, optional | Present only on `hd1k_combo`, value `0`. See below. |

**`format`** is derived from the diskdef name in `versions/<ver>/disks.json`:
`"hd1k_combo"` when the diskdef starts with `wbw_hd1k_`, otherwise `"hd1k"`
(`tools/gen_catalog.py:174`). It tells a client the on-disk layout. An `hd1k`
image is one 8388608-byte slice: 512 bytes/sector, 16 sectors/track, 1024
tracks, 4096 block size, 1024 directory entries, 2 boot tracks. An `hd1k_combo`
is a 1048576-byte MBR prefix (RomWBW's hd1k partition type is `0x2E`) followed
by six of those slices. A client that only mounts a whole image can ignore
`format`; a client that offers slice selection needs it.

**`bootable`, `cbios` and `host_transfer` describe one slice, not the whole
image.** For a combo the probe is slice 0 (`tools/gen_catalog.py:164` picks
`inject_utils[0]`, `"wbw_hd1k_0"`); for a single-slice image it is offset 0.
Slice 5 of the 3.5.1 combo is not bootable, and the entry says
`"bootable": true` because slice 0 is.

**`bootable`** comes from the boot track — the first 16384 bytes of the slice
(2 tracks × 16 sectors × 512) — and specifically from whether that region is
more than one repeated byte (`tools/diskinfo.py:104`). An hd1k image that was
never made bootable is left at the CP/M fill byte `0xE5`, uniformly non-zero,
so "any byte set" would call every data disk bootable. In 3.5.1, eleven of the
twenty published images are `false`: games, aztecc, bascomp, cowgol, fortran,
hitechc, tpascal, z80asm, ws4, msxroms1, msxroms2. In 3.6.0 every published
image is `true` — upstream made nearly all of them bootable.

**`cbios`** is the `CBIOS v<ver> [<platform>]` banner assembled into that boot
slice, e.g. `"CBIOS v3.5.1 [WBW]"`, or null when there is none. It matters
because RomWBW's own CBIOS — Z80 code inside the disk image — compares itself
against what `HBF_SYSVER` returns and prints
`*** WARNING: HBIOS/CBIOS Version Mismatch ***` when they differ. Upstream
compares **major and minor only** (`LD A,D` / `CP ((RMJ<<4)|RMN)`), so 3.5.0
against 3.5.1 does not warn and 3.5.x against 3.6.x always does, in both
directions. So `cbios` is what has to agree with the ROM's `hcb`.

A null `cbios` does not mean "not bootable". CP/M 3 and ZPM3 slices load
`BIOS3.SPR` and carry no banner at all, and their entries are
`"bootable": true, "cbios": null`. That is why `bootable` is measured from the
boot track and not from the banner: a banner test alone would report them as
data-only and the catalog would then tell the user something false.

A `-dev.NN` banner is reported verbatim rather than normalised
(`tools/diskinfo.py:27-29`), because a development snapshot has the same HCB
bytes as the release it precedes and the banner is the only thing that can tell
them apart.

**`host_transfer`** is true when the probed slice's CP/M directory contains both
`w8.com` and `r8.com` (`tools/gen_catalog.py:183`, `tools/diskinfo.py:107`).
Only `hd1k_combo` has it, in both published versions. It is stated rather than
implied by the description so a client can decide whether to offer host file
transfer at all for a given disk. `tools/verify_catalog.py` additionally checks
that the claim matches reality in both directions — a disk claiming
`host_transfer` must have both `w8.com` and `r8.com` in the probed slice's
directory, and one that does not claim it must not have them — and that the
three-byte `HBF_HOST_CAPS` probe `06 E9 CF` is inside that `w8.com`. It reads
the file out of the CP/M directory rather than scanning the image, because
three bytes occur somewhere in 51 MB by chance and an image-wide search would
pass on a `w8.com` that had lost the probe entirely. See
[INTERFACE_V0.md](INTERFACE_V0.md) for what that interlock guarantees.

**`defaultSlot`** is the slice a client should boot from when it mounts this
image with no other instruction. It exists only on `hd1k_combo`, value `0`, and
it is the one field the currently shipped `disks.xml` also carries. Absent means
"no opinion" — for a single-slice image there is nothing to choose.

**`slices`** is the count of slices in the image, present only when `format` is
`"hd1k_combo"`. It is what a slice picker enumerates.

**`upstream`** (the disk-entry string) records the file inside the RomWBW
package that this image started as. Every published image is the stock upstream
image with at most `W8.COM` and `R8.COM` added, and those are added only to
slice 0 of `hd1k_combo` — which is exactly what every shipped client already
has today. The built combo differs from the stock upstream image in 8234 bytes
across 24 runs, all of it `w8.com`, `r8.com` and their two directory entries.
The field lets anyone reproduce that comparison.

## 4. The `generation` contract

`generation` is a monotonic integer that advances **only when the artifacts
change**. Both halves of that sentence are load-bearing, and they pull in
opposite directions, which is why neither a hand-incremented number nor a
content hash is used on its own.

### 4.1 Why it has to be exactly this

iOS treats a change to this value as an instruction to delete files.
`checkCatalogVersionAndInvalidate` reads the `UserDefaults` key
`"catalogVersion"`; when the published value differs it calls
`deleteCatalogDisks(named: catalogFilenames)` and shows an alert titled
"Disk Catalog Updated". A spurious change destroys a user's downloaded library.

- A **hand-incremented number** moves when nothing moved. Somebody fixes a typo
  in a description, bumps the number out of habit, and every iOS user loses
  201 MB of downloads for a spelling correction.
- A **content hash** never moves spuriously, but it is not monotonic and not an
  integer. It cannot answer "is this newer".

So: hash the content, and bump a stored counter only when the hash changes.

### 4.2 How it is computed

`catalog_generation` in `tools/gen_catalog.py:75-112`:

1. Build a payload of `[filename, sha256]` pairs — ROMs first, then disks — and
   take its sha256 (`tools/gen_catalog.py:88-92`).
2. Read `versions/<ver>/generation.json`. If it is missing, start from
   `{"generation": 0, "content_sha256": null}`.
3. If the stored `content_sha256` differs from the new digest, write back
   `generation + 1` with the new digest. Otherwise leave the file alone and
   return the stored counter.

`versions/<ver>/generation.json` holds three keys: `generation` (integer),
`content_sha256` (string), and a `_comment` saying it is machine-written. Both
published versions are currently at `generation: 1` — the first run of the
generator took each from 0 to 1.

Two consequences worth stating plainly:

- **Only filenames and hashes feed the digest.** Changing a `name`, a
  `description`, a `license` or a `notes` entry does not bump the generation and
  does not delete anyone's library. That is deliberate: catalog copy should be
  fixable without cost.
- **The pair list is sorted before hashing.** `tools/gen_catalog.py`'s
  `content_digest` calls `sorted()` on the pairs, so reordering entries in
  `versions/<ver>/roms.json` or `disks.json` is a no-op: same files, same
  hashes, same digest, same generation. This matters because the obvious
  implementation — `json.dumps(..., sort_keys=True)` — does **not** do it.
  `sort_keys` orders dict keys, and the payload is a list of lists, so a pure
  reorder of a manifest silently bumped the generation and deleted every iOS
  user's downloaded images.
- **The counter never decreases.** A lost, reverted or hand-edited
  `generation.json` cannot roll it back: `catalog_generation` takes a floor
  from the `generation` in the committed `catalog/v0/<ver>/catalog.json`,
  which is in git. If the artifacts still match what that committed catalog
  describes, the published number is adopted rather than a new one invented —
  a spurious bump costs every user their library.

### 4.3 It is per RomWBW version

The counter file lives at `versions/<ver>/generation.json` — one per RomWBW
version. 3.5.1 and 3.6.0 each have their own, and they advance independently.

This is required, not incidental. A user switching 3.5.1 → 3.6.0 → 3.5.1 is not
making three catalog changes, and must not have their library deleted twice. If
the counter were global, every publication under any version would invalidate
every version's downloads.

**What this asks of a client:** a client that supports more than one RomWBW
version must store its remembered `catalogVersion` **per RomWBW version**, the
same way it must namespace its NVRAM blob per version. One shared
`UserDefaults` key across versions re-creates the exact deletion loop the
per-version counter was built to prevent — and it will not be obvious today,
because both published versions happen to be at generation 1. The NVRAM problem
is the same shape: RomWBW's `NVSW_CHECKSUM` XORs the version bytes into the
seed, so a blob saved under 3.5.1 fails validation under a 3.6.0 ROM and
silently resets to defaults, and iOS stores it under one key `"emulatorNvram"`.
See [CLIENT_MIGRATION.md](CLIENT_MIGRATION.md).

### 4.4 How a client should use it

Compare for equality against the stored value, act, store the new value. Do not
do arithmetic on it. A client that skipped several publications will see a jump
of more than 1, and that is normal.

## 5. The legacy disks-v0-&lt;ver&gt;.xml

`write_legacy_xml` (`tools/gen_catalog.py:231-259`) emits the same disks in the
shape every client already parses. The point is to split one migration into two
releases: a client can point at the new URL while still running its old parser,
then learn the JSON in a later release.

It is published as `disks-v0-<ver>.xml` on the version's release tag, and its
URL is the index entry's `disks_xml_url`.

### 5.1 Exactly what it emits

An XML declaration, then a root `<disks>` element with three attributes
(`tools/gen_catalog.py:245-247`):

| Attribute | Value | Notes |
|---|---|---|
| `version` | the catalog `generation`, as a decimal string | Currently `"1"` for both versions. |
| `interface` | `"v0"` | New in this repo. |
| `romwbw` | `"3.5.1"` / `"3.6.0"` | New in this repo. |

Then one `<disk>` element per catalog disk entry, in catalog order. Each
`<disk>` contains, in this order (`tools/gen_catalog.py:250-256`):

- `<filename>`
- `<name>`
- `<description>`
- `<size>`
- `<license>`
- `<sha256>`
- `<defaultSlot>` — **only** when the catalog entry has one, so only on
  `hd1k_combo`

That is the complete list. The XML does **not** carry `id`, `format`,
`bootable`, `cbios`, `host_transfer`, `upstream` or `slices`, and it carries no
ROMs at all. Anything past the disk list needs the JSON.

Output is pretty-printed with four-space indent.

### 5.2 The two new attributes, and the one that bites

`interface=` and `romwbw=` are additions. They are safe because no current
parser reads any attribute except one. Verified: `cpmdroid`'s `parseDisksXml`
(`DiskCatalogRepository.kt:91-140`) makes zero `getAttribute` calls, and
`z80cpmw` reads none either (`DiskCatalog.cpp:29-30`). Only iOS reads an
attribute, and only `version`.

Which is the one that bites. The catalog shipped today is `<disks version="13">`.
This document starts at `version="1"`, per RomWBW version. The first iOS client
that points at this URL sees 13 → 1, `checkCatalogVersionAndInvalidate` fires,
and it deletes its catalog-named disks once. That is unavoidable and mostly
moot: every filename changes under the `<id>-v0-<ver>` convention anyway, so the
old downloads would be orphaned regardless, and saved-state identity in all
three clients is filename-only. The migration has to be planned rather than
stumbled into; [CLIENT_MIGRATION.md](CLIENT_MIGRATION.md) covers it.

## 6. Compatibility rules

Interface v0 promises these two documents keep their shape. Everything below
follows from that.

### 6.1 What a client MUST tolerate

**Unknown fields, everywhere.** A client must ignore fields it does not know, at
every level: top level, `romwbw_versions[]`, `hbios`, `roms[]`, `hcb`,
`built_from`, `disks[]`, `upstream`. New fields will be added. A parser that
rejects an unrecognised key, or that round-trips the document and drops
unrecognised keys, is broken by the next release.

**New RomWBW versions appearing in the index.** Adding RomWBW 3.7.0 is a new
release tag and a regenerated index. No client change, no interface bump. A
client that filters on `hbios.ver_byte` / `upd_byte` simply will not match the
new entry until it is rebuilt.

**New `roms[]` and `disks[]` entries, and entries disappearing.** `hd1k_ws4`
exists under 3.5.1 and not under 3.6.0. `roms[]` has two entries today; do not
hardcode two, and do not assume `emu_avw` is present. Key on `id`, not on array
position and not by parsing `filename`.

**`notes` changing.** Text edits, new entries, entries removed, and an empty
array are all normal. Never branch on note text.

**Optional and nullable fields being absent or null.** `slices` and
`defaultSlot` appear only on `hd1k_combo`. `cbios` is null on CP/M 3 and ZPM3
slices and on every data-only image. `released` and `package_sha256` are read
with `.get()` and can be null.

**`generation` jumping by more than 1.** Compare, do not compute.

**New `status` and `license` values.** Both are free text copied from the
version metadata. `"stable"` and `"preview"`, and `"Mixed"`, `"Abandonware"`,
`"Freeware"`, `"Open Source"`, are what is in use — not a closed enum. Display
unknown values; do not fail on them.

**`base_url` ending in `/`.** Concatenate `base_url + filename`. Do not insert
a separator. This is the exact spot where the three current clients disagree
today: iOS's base has no trailing slash and its parser appends `"/" + filename`,
while Android's and Windows's bases do have one. Under v0 the trailing slash is
in the document, so the client-side fixup must go.

**Sizes other than 8388608 and 51380224.** Nothing in the schema promises a
size. Upstream v3.6.0 already ships ROM images that are not 512KB.

**Exactly one `default: true` in the index — but fall back sanely.** The
generator's release check enforces it (`tools/verify_catalog.py:165-167`), so a
published index will have exactly one. A client should still pick something
reasonable rather than crash if it ever sees zero or two.

### 6.2 What would be a v0 → v1 break

The general rule is in [INTERFACE_V0.md](INTERFACE_V0.md#when-to-bump-to-v1):
bump when an existing client would *misbehave* rather than merely miss out. For
this schema specifically, these are breaks:

- removing a field documented above, or reusing its name for a different meaning
- changing a field's type — for instance making `hcb.version` an integer to
  match `hcb.platform`, or making `ver_byte` an integer
- changing `base_url` so it no longer ends in `/`
- changing the `<id>-v0-<ver>.<ext>` asset naming, or the `v0-romwbw-<ver>` tag
  naming
- changing what `generation` means, including making it advance for reasons
  other than an artifact change

These are **not** breaks: adding a field, adding a RomWBW version, adding or
removing a ROM or a disk, editing a name or description, editing `notes`.

A v1 would live alongside v0 — new release tags, a new index URL, v0 tags
untouched. GitHub release asset URLs cannot be redirected, so every tag this
repo publishes has to stay live for as long as any client points at it.

## 7. Worked example: getting `hd1k_combo-v0-3.5.1.img`

Three fetches.

**1. The index.** The one URL compiled into the client.

```
GET https://github.com/avwohl/romwbw_disks/releases/download/catalog-v0/index-v0.json
```

Walk `romwbw_versions[]` and keep what this build can run. A shipped client's
bundled core is built for RomWBW 3.5.1, so it keeps the entry whose
`hbios.ver_byte` is `"0x35"` and `hbios.upd_byte` is `"0x10"` —
`romwbw_version` `"3.5.1"`, `status` `"stable"`, `default` `true`,
`generation` `1`. It has not downloaded a single byte of ROM to work this out.

A client rebuilt on `romwbw_emu` v1.39 or later asks its core per entry
(`emu_romwbw_release_supported({ver_byte, upd_byte})`) instead of comparing
against a constant, and on today's core keeps the 3.6.0 entry as well. The rest
of this example follows the 3.5.1 entry.

**2. That entry's `catalog_url`.**

```
GET https://github.com/avwohl/romwbw_disks/releases/download/v0-romwbw-3.5.1/catalog-v0-3.5.1.json
```

Verify against the index entry before parsing:

```
catalog_size    11826
catalog_sha256  7a5411b329be606c2bcc7b8d2b051b8fca9a2906f780d65fc98221cb6b61ed65
```

Compare the catalog's `generation` (`1`) against the stored value for RomWBW
3.5.1. If it differs, this is when downloaded images for **this RomWBW version**
are invalidated — not for any other version.

**3. The asset**, as `base_url + filename`. `base_url` is
`https://github.com/avwohl/romwbw_disks/releases/download/v0-romwbw-3.5.1/` and
the entry with `"id": "hd1k_combo"` has
`"filename": "hd1k_combo-v0-3.5.1.img"`, so:

```
GET https://github.com/avwohl/romwbw_disks/releases/download/v0-romwbw-3.5.1/hd1k_combo-v0-3.5.1.img
```

Verify against the catalog entry:

```
size    51380224
sha256  0ca4ec60cb8bca71b8f0287c4b634c3126887be483db9b59b41bdff424f89303
```

The rest of that entry tells the client how to present it:
`format` `"hd1k_combo"` and `slices` `6` mean six selectable 8MB slices behind a
1MB MBR prefix; `defaultSlot` `0` means boot slice 0 unless told otherwise;
`bootable` `true` and `cbios` `"CBIOS v3.5.1 [WBW]"` mean slice 0 boots and its
CBIOS matches the ROM, so no `HBIOS/CBIOS Version Mismatch` warning; and
`host_transfer` `true` means host file transfer can be offered on this disk.

The matching ROM comes from the same catalog's `roms[]`:
`emu_avw-v0-3.5.1.rom`, `size` `524288`, `sha256`
`4b11402a29fad22de304775b7c415eb6a74600df06bd57828b9931a7e9693258` — which is
byte-identical to the `emu_avw.rom` bundled in `ioscpm`, `cpmdroid`, `z80cpmw`
and `romwbw_emu` today. Its `hcb.version` `"0x35"` and `hcb.update` `"0x10"`
are the bytes `emu_validate_rom_hcb` will read at `0x105`/`0x106` after the
download, so a client that checked them in step 1 already knows the load will
succeed.

To check the same thing from outside, download a tag's assets into a directory
and run `tools/verify_catalog.py <catalog.json> <asset-dir>`. It re-reads the
artifacts and re-derives every claim rather than trusting the generator.
