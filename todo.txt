The original brief that started this repository is gone from this file because
every line of it is done: the two-level catalog exists and is published, disk
and ROM filenames carry the interface and the RomWBW release, 3.5.1 and 3.6.0
are both built and verified, w8.com/r8.com/emu_hbios.asm/emu_rom.asm live in

- [WINDOWS + MAC + ANDROID] NONE OF THE CLIENT MIGRATION HAS BEEN COMPILED, and
that is the largest open item anywhere in this family.  ioscpm builds 63-64,
cpmdroid 1.26-1.27 and z80cpmw's unreleased entry were all written on a Linux
machine with no Xcode, no Android SDK or NDK and no MSVC.  What could be checked
without them was, and each client's CHANGELOG says which tier each file reached:
cpmdroid type-checked every Kotlin source and ran three JVM suites (20 + 14 + 3),
z80cpmw compiled and ran tests/test_catalogv0.cpp (107 checks) and syntax-checked
six more sources under mingw, ioscpm checked its project.pbxproj edits and its
ObjC bridge by reading.  What reached no compiler at all is ioscpm's Swift, and
z80cpmw's MainWindow.cpp and SettingsDialogWx.cpp - which between them hold the
F5 default-disk path, the Settings write-back and the release picker.  Each
client's MANUAL_CHECKS.md lists what a person has to drive.  Until that happens
none of this is known to work.

- [ANY] 3.6.0 is "status": "stable" as of 2026-09-05 and "default": false, and
those are two different gates on purpose.  Status was promoted on the emulator
evidence: romwbw_emu v1.39 boots it and tools/boot_test.sh asserts the boot, the
banner, the absence of a mismatch warning and an R8/W8 round trip every run.
default stays false because no released client carries that core, and a client
should not PREFER a release its own shipped builds cannot run.  A shipped client
is not endangered by the promotion - it filters the index by hbios.ver_byte
against what its core supports, so 3.6.0 never survives that filter on a
pre-v1.39 build; the version bytes are the safety mechanism, the label is not.
  Move default to 3.6.0 when a released ioscpm, cpmdroid or z80cpmw carries a
  v1.39+ core.  Promotion is index-only: edit version.json, run
  tools/gen_catalog.py --index, publish index-v0.json to the floating catalog-v0
  tag, and never re-cut the immutable per-version assets - which is why
  check_committed.py now allows a published catalog saying "preview" under a
  manifest saying "stable", in that direction only.

- [ANY] DECIDED 2026-09-05: the pre-v0 hd1k_combo is accepted as equivalent and
NOT refreshed.  What is left is carrying that into the clients.  The two images
were compared byte for byte - the published v1.4.12 asset against the one built
here - and all 2,342 differing bytes of 51,380,224 fall inside slice 0, in CP/M
slack and directory padding.  The slice 0 directory lists the same 94 files,
every one of them is byte-identical including r8.com and w8.com, and slices 1-5
do not differ at all.  Two toolchains wrote the same files into the same slice
and left different garbage between them.  docs/FINDINGS.md section 10 has the
measurements and the reasoning; spending 49 MB of every migrated user's data to
replace an image whose every file already matches is not defensible.
  The equivalence belongs in each client's MIGRATION, not in the catalog: it is
  a fact about what the migration renamed, not about what v0 publishes, and the
  3.5.1 catalog is on an immutable tag either way.  ioscpm is the only client
  that would act unattended and so the only one that must change; z80cpmw
  computes the verdict and calls nothing, cpmdroid compares filenames.  Two
  limits on the exception: never accept it for an image the client DOWNLOADED,
  and drop it once a device has fetched the canonical combo.

- [ANY] the original brief's last question is ANSWERED: only one client still

- [ANY] cleanup: three of four are DONE 2026-09-05, and the fourth must NOT be
done.  Deleted: romwbw_emu/disks/disks.xml (an inventory of nothing - 19 of its
21 filenames named images that repo does not track, and it never listed one of
the two it does); romwbw_emu/archive/romwbw-v3.6.0/SBC_simh_std_v360.rom (a
3.6.0-dev.46 snapshot whose HCB is indistinguishable from the release, so no

z80cpmw/packaging/scripts/verify-disk-assets.sh (that package has no images to
check any more, and it was the last um80 consumer in any client).  Each was
verified not to break anything first - `make -C src test` still passes in
romwbw_emu with the three counts CI asserts unchanged, and verify_romwbw_pin.sh
prints byte-identical output before and after the archive deletion.
  NOT the duplicated Z80 sources in romwbw_emu/src.  That one is listed in
  docs/CLIENT_MIGRATION.md step 6 and it is wrong: r8.asm, w8.asm, emu_hbios.asm
  and emu_rom.asm have SEVEN live consumers in that repo, because romwbw_emu
  still builds and verifies its own bundled ROM and its own two tracked disk
  images from them - disks/rebuild_disk_utils.sh assembles them,
  disks/verify_disk_utils.sh checks the result, roms/build_from_source.sh builds
  the ROM, src/makefile's test target runs the first, and CI asserts the counts.
  Deleting them is not cleanup; it would be a decision to make romwbw_emu a
  consumer of romwbw_disks' published artifacts, and it would need a replacement
  for all of that first.  Having the same file in two repositories is the price
  of the two repositories building independently.  Nothing checked the copies
  against each other until 2026-09-05; tools/check_source_drift.sh does now, and
  they agree: r8.asm, w8.asm and emu_rom.asm are byte-identical, emu_hbios.asm
  differs only by taking its version from the generated romwbw_ver.inc instead of
  a hardcoded db 035h, and both trees build emu_avw.rom to the same
  c7abc580... - which is what proves the parameterisation is the only difference.
  r8.com and w8.com assemble identically too, so the two um80 installations agree
  as well as the two sources do.

- [ANY] the ioscpm release tags stay live forever regardless of the migration.
Every build already in users' hands is hardwired to
releases/download/v1.4.12/, GitHub release asset URLs cannot be redirected, and
