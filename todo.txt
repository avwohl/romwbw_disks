- [ANY] the HBIOS dispatcher diff for 3.6.0 IS DONE, 2026-09-05, and it found
six real bugs - all of them in romwbw_emu, all now fixed (romwbw_emu aa52c9e).
  The result was not the expected one.  NOTHING changed contract between 3.5.1
and 3.6.0: all 124 BF_* equates resolve identically and a block-by-block read of
hbios.asm found no register, unit or side-effect change in any function the core
implements.  What changed is REACHABILITY.  3.6.0 moved the boot loader's device
inventory out of the HBIOS bank into a ROM app (Source/HBIOS/invntdev.asm), and
our proxy REPLACES that bank - so code that used to be ours now runs against the
dispatcher and read back six answers that had been wrong all along with no
caller to notice.  BF_DIOCAP had DE and HL swapped (a 49MB disk reported as
65536MB, and COPYSL.COM reads the same value from CP/M, so it was never confined
to a diagnostic screen); BF_DIODEVICE left the device-class nibble at zero;
BF_VDAQRY had rows and columns reversed; BF_VDADEV had no case at all;
BF_SNDQUERY ignored its subfunction; and BF_CIOQUERY answered the wrong question
- that last one being the only of the six 3.6.0 did NOT make reachable, since
MODE.COM ships on the published images and read it wrong on 3.5.1 too.
Also fixed: an unimplemented CIO, DIO or SYS function called emu_fatal(), so a
guest could kill the emulator process by asking for something unimplemented.
  Two things this repository's own docs got WRONG and which are now corrected in
docs/FINDINGS.md: the claim that unimplemented functions answer HBR_NOFUNC (only
the EXT group did - CIO/DIO/SYS aborted and RTC/VDA/SND returned success with
stale registers), and BF_SNDNOTE's "quarter note" -> "eighth tone" change, which
was cited as a semantic change and is a terminology CORRECTION: the note tables
are byte-identical and 48 steps per octave really is eight per whole tone.
  A SECOND pass then checked all 82 implemented functions against RomWBW's own
handlers rather than against the previous release - which is where the bugs
actually were, since five of the first six were "implemented but wrong".  It
produced 74 findings and around 30 are now fixed across romwbw_emu commits
68d02ac..aceaa84: a guest-visible console hang (BF_CIOIST returning $FF, which
reads as a negative error, so HTALK.COM span forever), swapped memory-disk
geometry, a heap that grew on every OS boot, no periodic timer at all
(TIMER.COM frozen, VGMPLAY.COM hung), slice bounds checked against the wrong
end of the wrong thing, six SYS subfunctions answering in the wrong register,
all three SND setters reading the wrong register, and unhandled VDA/SND/RTC
functions reporting SUCCESS with the caller's own registers.
  Two things are deliberately NOT done and are recorded in romwbw_emu's todo:
HB_BNKCALL, because the clean fix changes bank 0 of every published ROM and so
forces a generation bump and a republish of both releases; and the remaining
low-severity findings, which are catalogued in that audit and are contract
tidying rather than defects a user meets.
  What is still not done is the rest of hbios.asm.  These passes covered the
boot path, the device inventory, every function the dispatcher implements, and
the new 3.6.0 surface.  They did not read all 268KB.

- [ANY] tools/publish_release.sh is undocumented, contradicts section 6 of
docs/RELEASING.md, and CANNOT SAFELY PUBLISH A CORRECTION.  It appears in neither
that document's procedure nor tools/README.md's script table, and at :177-178 it
sets --prerelease from version.json's status - which section 6 rules out, because
a client must read status from the index and never infer it from a GitHub flag.
  The third fault is the dangerous one and was found on 2026-09-06 while
publishing the HB_BNKCALL rebuild.  It decides an asset is already uploaded by
comparing SIZE.  Every ROM is 512 KB before and after any change to bank 0, so on
a respin it silently skips all four rebuilt ROMs while still uploading the
catalog that hashes the new bytes - publishing a catalog whose every ROM entry
fails verification in every client.  Nothing in the script reports the skip as
anything but success.  That publish was therefore done by hand with --clobber.
  Either fix it to compare sha256 and wire it into RELEASING.md properly, or
delete it before someone runs it expecting section 4's behaviour.

- [ANY] STANDING: do NOT delete the duplicated Z80 sources in romwbw_emu/src.
docs/CLIENT_MIGRATION.md step 6 listed them as cleanup and listing them was
wrong.  r8.asm, w8.asm, emu_hbios.asm and emu_rom.asm have seven live consumers
in that repository, because romwbw_emu still builds and verifies its own bundled
ROM and its own two tracked disk images from them - rebuild_disk_utils.sh
assembles them, verify_disk_utils.sh checks the result, build_from_source.sh
builds the ROM, src/makefile's test target runs the first, and CI asserts the
counts.  Deleting them would not be cleanup; it would be a decision to make
romwbw_emu a consumer of what this repository publishes, and it needs a
replacement for all of that first.
  Having the same file in two repositories is the price of the two building
independently.  tools/check_source_drift.sh compares them on every push, and
they agree: three are byte-identical, emu_hbios.asm differs only by taking its
version from the generated romwbw_ver.inc, and both trees build emu_avw.rom to
the same 4b11402a....
  The other three cleanup items were done on 2026-09-05: romwbw_emu's
disks/disks.xml and its archive/romwbw-v3.6.0 dev snapshot, and z80cpmw's
packaging/scripts/verify-disk-assets.sh.  Each was verified not to break
anything first; the commit messages carry the evidence.

SETTLED DECISIONS AND STANDING FACTS, KEPT ONLY AS POINTERS
-------------------------------------------------------------------------------
Nothing here is a task.  Each was either decided rather than merely done - and a
decision that leaves no trace gets re-litigated - or is a constraint that will
never be "done" and has to keep being true.  The reasoning is where the pointer
says, not repeated here.

- The clients fetch the ROM from the catalog (2026-09-05): ioscpm build 65
  cf8d2f7, cpmdroid bb0ac74, z80cpmw 17c72fa.  A new RomWBW version now needs a
  release HERE and nowhere else, which was the point of this repository.  The
  bundled ROM stays as a first-launch fallback and is byte-identical to the
  published emu_avw-v0-3.5.1.rom.  ioscpm's docs/ROM_ATTESTATION.md was rewritten
  to describe the download; filing it is a person's job and ioscpm's todo has it.

- The pre-v0 hd1k_combo is equivalent and is NOT refreshed: 19 of 20 published
  images are byte-identical across the two catalogs, and the combo's 2,342
  differing bytes are CP/M slack between the same 94 identical files.
  docs/FINDINGS.md section 10 has the measurements.  Implemented in ioscpm and
  z80cpmw, keyed on provenance so a downloaded image can never be blessed by it;
  cpmdroid needed no change and its todo warns whoever adds image hashing.

- Only one client ever needed um80, and none builds Z80 code in its own build.
  It was z80cpmw's packaging/scripts/verify-disk-assets.sh, deleted 2026-09-05
  once its 06 e9 cf HBF_HOST_CAPS probe was confirmed asserted here instead - at
  build time in tools/build_utils.sh and against every published image carrying
  w8.com in tools/verify_catalog.py.

- The ioscpm release tags stay live forever regardless of the migration.
Every build already in users' hands is hardwired to
releases/download/v1.4.12/, GitHub release asset URLs cannot be redirected, and
in-app help on both ioscpm and z80cpmw still fetches help_index.json from
avwohl/ioscpm/releases/latest.  Migrating the disk catalog frees nothing there;
retiring those tags would break installed clients and in-app help at once.
