Todo list.  Open items only.  What this repository is and why is in README.md;
the contract is docs/INTERFACE_V0.md, the wire format docs/CATALOG_SCHEMA.md,
the build and publish procedure docs/RELEASING.md, and what was measured about
the old system docs/FINDINGS.md.  Finished work is in the commit messages that
made it.

Every item carries a tag saying what a machine has to be able to do to take it,
so a session on another OS can see at a glance what it can pick up.

The original brief that started this repository is gone from this file because
every line of it is done: the two-level catalog exists and is published, disk
and ROM filenames carry the interface and the RomWBW release, 3.5.1 and 3.6.0
are both built and verified, w8.com/r8.com/emu_hbios.asm/emu_rom.asm live in
src/, and all three GUI clients were migrated on 2026-09-05.  Its last question
is answered under [ANY] below.

- [WINDOWS + MAC + ANDROID] NONE OF THE CLIENT MIGRATION HAS BEEN COMPILED, and
that is the largest open item anywhere in this family.  ioscpm builds 63-64,
cpmdroid 1.26-1.27 and z80cpmw's unreleased entry were all written on a Linux
machine with no Xcode, no Android SDK or NDK and no MSVC.  What could be checked
without them was, and each client's CHANGELOG says which tier each file reached:
cpmdroid type-checked every Kotlin source and ran three JVM suites (20 + 14 + 3),
z80cpmw compiled and ran tests/test_catalogv0.cpp (107 checks) and syntax-checked
six more sources under mingw, ioscpm checked its project.pbxproj edits and its
ObjC bridge by reading.  What reached no compiler at all is ioscpm's Swift, and
z80cpmw's MainWindow.cpp and SettingsDialogWx.cpp - which between them hold the
F5 default-disk path, the Settings write-back and the release picker.  Each
client's MANUAL_CHECKS.md lists what a person has to drive.  Until that happens
none of this is known to work.

- [ANY] 3.6.0 stays "status": "preview" and "default": false, and the exit
condition is a released client, not a working emulator.  romwbw_emu v1.39 boots
it and tools/boot_test.sh proves it, but no build in any store carries that core
or the v0 catalog reader.  Flip status in versions/3.6.0/version.json, regenerate
and republish only when a shipped ioscpm, cpmdroid or z80cpmw can load a 3.6.0
ROM.  docs/RELEASING.md's "Known open work" states the same criterion.

- [ANY] DECIDED 2026-09-05: the pre-v0 hd1k_combo is accepted as equivalent and
NOT refreshed.  What is left is carrying that into the clients.  The two images
were compared byte for byte - the published v1.4.12 asset against the one built
here - and all 2,342 differing bytes of 51,380,224 fall inside slice 0, in CP/M
slack and directory padding.  The slice 0 directory lists the same 94 files,
every one of them is byte-identical including r8.com and w8.com, and slices 1-5
do not differ at all.  Two toolchains wrote the same files into the same slice
and left different garbage between them.  docs/FINDINGS.md section 10 has the
measurements and the reasoning; spending 49 MB of every migrated user's data to
replace an image whose every file already matches is not defensible.
  The equivalence belongs in each client's MIGRATION, not in the catalog: it is
  a fact about what the migration renamed, not about what v0 publishes, and the
  3.5.1 catalog is on an immutable tag either way.  ioscpm is the only client
  that would act unattended and so the only one that must change; z80cpmw
  computes the verdict and calls nothing, cpmdroid compares filenames.  Two
  limits on the exception: never accept it for an image the client DOWNLOADED,
  and drop it once a device has fetched the canonical combo.

- [ANY] the HBIOS dispatcher diff for 3.6.0 is still not done.  Booting six
operating systems and round-tripping R8/W8 exercises a great deal of that
surface without enumerating it, and identical BF_* equates prove the function
numbers did not move, not that the behaviour behind one is unchanged.  What has
to be read is RomWBW's Source/HBIOS/hbios.asm (263,153 bytes in 3.5.1, 267,954 in
3.6.0) and Source/Doc/SystemGuide.md against the emulator's dispatcher.  There is
no proto.asm and never was; docs/ROMWBW_VERSIONS.md carries the detail.

- [ANY] tools/publish_release.sh is undocumented and contradicts section 6 of
docs/RELEASING.md.  It appears in neither that document's procedure nor
tools/README.md's script table, and at :177-178 it sets --prerelease from
version.json's status - which section 6 rules out, because a client must read
status from the index and never infer it from a GitHub flag.  Either wire it into
RELEASING.md properly or delete it before someone runs it expecting section 4's
behaviour.

- [ANY] the original brief's last question is ANSWERED: only one client still
needs um80, and no client builds Z80 machine code as part of its own build.
Measured 2026-09-05 by grepping all three trees - the single consumer is
z80cpmw/packaging/scripts/verify-disk-assets.sh, which assembles r8.asm and
w8.asm to compare against what a disk image carries.  ioscpm and cpmdroid have
none: ioscpm's Xcode project runs zero shell script build phases and holds no
.asm at all.  That script can go once its 06 e9 cf HBF_HOST_CAPS probe is known
to be covered here instead - it is, at tools/build_utils.sh build time and in
tools/verify_catalog.py against every published image carrying w8.com - but note
before deleting it that it fails 8 of the 20 v0 images for an unrelated reason,
so repointing it is not a one-line change.

- [ANY] cleanup still outstanding in the sibling repos, now that no client reads
a disks.xml from an ioscpm tag: romwbw_emu/disks/disks.xml is a dead third

- [ANY] the ioscpm release tags stay live forever regardless of the migration.
Every build already in users' hands is hardwired to
releases/download/v1.4.12/, GitHub release asset URLs cannot be redirected, and
in-app help on both ioscpm and z80cpmw still fetches help_index.json from
avwohl/ioscpm/releases/latest.  Migrating the disk catalog frees nothing there;
retiring those tags would break installed clients and in-app help at once.
